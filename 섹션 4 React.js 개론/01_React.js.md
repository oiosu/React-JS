### 01_React.js

* Meta(Facebook) 이 개발한 오픈소스 자바스크립트 라이브러리 
* 대규모 웹 서비스의 UI를 더 편하게 개발하기 위해 만들어진 기술
* 제공하는 기능이 매우 강력하기 때문에 넷플릭스, 페이스북, 인스타그램, 노션처럼 대규코 서비스들을 지탱하고 있는 기술로서 활발히 사용이 되고 있음

---

##### ◼️ React의 기술적인 특징 (핵심)

(1) 컴포넌트를 기반으로 UI를 표현한다.

(2) 화면 업데이트 구현이 쉽다. 

(3) 화면 업데이트가 빠르게 처리된다. 

---



##### (1) 컴포넌트를 기반으로 UI를 표현한다.

◼️ **Component** : 우리말로 구성요소 라는 뜻이다 

(화면을 구성하는 요소, UI를 구성하는 요소를 말한다.)

> * Header ===> Header.js
> * Main ===> Main.js
> * Footer === Footer.js 

> 각각의 자바스크립트 파일에 component 라는 단위로 나눠서 모듈화해서 보관할 수 있기 때문에 웹페이지를 레고를 조립하듯이 여러개의 컴포넌트들을 합쳐서 만들어 낼 수 있다.

> 즉 컴포넌트를 우리가 자바스크립트 파일로 모듈화 할 수 있다는 것은 중복 코드를 제거하는 관점에서 매우 큰 장점이 된다.

* 리액트에서는 기본적으로 페이지의 모든 요소들을 컴포넌트라는 단위로 모듈화해서 개발하기 때문에 여러 페이지에서 공통으로 사용되는 요소가 필요할 때 Header 컴포넌트를 만들고 이 컴포넌트를 여러 페이지에서 불러와서 사용하도록 만들면 되기 떄문에 중복 코드가 발생하지 않게 된다.
* 따라서 수정사항이 발생한다고 하더라도 컴포넌트 하나만 수정해주면 되기 때문에 유지보수의 차원에서 용이하다.

##### (2) 화면 업데이트 구현이 쉽다. 

◼️ **Update** : 사용자의 행동(클릭, 드래그)에 따라 웹 페이지가 스스로 모습을 바꿔 상호작용하는 것 

![image-20240615163941156](https://raw.githubusercontent.com/oiosu/image_repo/master/img/image-20240615163941156.png)

* 리액트에서는 업데이트를 구현하기가 매우 쉽다.

  * Why: 리액트는 **선언형 프로그래밍**이라는 방식으로 동작하기 때문이다.

  | 선언형 프로그래밍                                            |
  | ------------------------------------------------------------ |
  | 과정은 생략하고 목적만 간결히 명시하는 방법 <br />마치 우리가 식당에서 주문하는 것과 유사함(토마토 파스타 하나 주세요) |

  > 토마토 파스타를 만드는 과정 자체는 잘 모르겠고 내 목적은 토마토 파스타 다 라고 목적만 선언형으로 이야기한다. 

  | 명령어 프로그래밍                                            |
  | ------------------------------------------------------------ |
  | 목적을 이루기 위한 모든 일련의 과정을 설명하는 방식 <br />마치 진상(?) 손님처럼 주문하는 방식 |

  > "주방으로 가서 면 100g을 꺼내세요 그리고 뜨거운 물에 9분간 삶으세요 그런 다음 후라이팬을 꺼내 불을 올리고 토마토 소스와 함께 볶으세요  다 되었다면 접시에 담아서 나에게 가져와 주세요"

  > 선연형 방식과 달리 명령어는 목적을 달성하기까지의 모든 과정을 하나하나 다 일일이 명시



* 리액트를 사용하지 않고 자바스크립트만 사용한다고만 하면 특별한 도구를 추가로 사용하지 않는 이상은 보통 명령형 프로그래밍 방식으로 모든 기능을 다 구현해야 되기 때문에 코드가 비교적 길고 복잡해질 수 있다.

* 리액트에서는 선언형 프로그래밍 방식으로 동작하기 때문에 아주 간단하게 화면을 업데이트 가능하다.

* **그 원리는 무엇일까?**

##### (3) 화면 업데이트가 빠르게 처리된다. 

* ##### [선수 지식 필요]

  * 브라우저는 어떻게 동작하는가? 
  * HTML, CSS 로 만든 페이지를 어떻게 렌더링 하는가?
  * 화면 업데이트는 어떻게 처리 되는가? 

  

##### ✅ 브라우저의 렌더링 과정(Critical Rendering Path)

![image-20240616180633148](https://raw.githubusercontent.com/oiosu/image_repo/master/img/image-20240616180633148.png)

* **1단계** : HTML, CSS 를 각각 DOM 이라는 것과 CSS Object 모델이라는 것으로 변환 (DOM이라는 건 HTML 문서를 일종의 객체 모델로 변환한 것)
  * DOM (Document Object Model)
  * CSS Object Model 또한 CSS 코드를 브라우저가 자기가 더 이해하기 쉬운 형태로 변환
* **2단계** : 모델로 변환을 하고 나면 DOM과 CSS Object Model을 합쳐서 렌더트리라는 것을 만들게 된다. 
  * Render Tree : 웹페이지의 청사진 또는 웹페이지의 설계도 정도의 역할을 한다.
  * DOM에는 우리가 HTML로 표현한 요소들의 위치나 배치 모양 등에 관해 정보가 있고 CSS 오브젝트 모델에는 CSS로 표현한 요소들의 스타일과 관련된 모든 정보가 있을 것이다. 
  * 그렇기 때문에 이 두개를 합쳐서 만든 렌더 트리에는 화면에 나타나야 되는 즉, 화면에 렌더링 되어야 하는 요소들의 모든 정보가 다 포함이 되어 있다.
  * 그렇기 때문에 렌더 트리를 웹페이지의 청사진이라고 부른다고 알아두면 좋다.
* **3단계** : 레이아웃이라는 작업을 수행한다. (Layout_요소의 배치를 잡는 작업) 
  * 레이아웃은 일상생활에서 방을 꾸민다고 할 때 침대 위치와 책상의 방향 등 방의 배치를 잡는 과정을 흔히 레이아웃을 잡다 이렇게 표현하게 된다. 
  * 웹 페이지라는 공간 안에 렌더트리에 포함되어 있는 요소들의 배치를 잡는 것 
* 4단계 : 페인팅이라는 작업을 수행한다.(Painting_실제로 화면에 그려내는 과정)
  * 요소를 실제로 화면에 그려내는 과정이다. 
  * 이 과정을 거치게 되면 웹페이지가 실제로 우리 눈앞에 나타나게 되는 것 



#### 🤔 그럼 업데이트는 언제 발생하게 되는 것? 

> 자바스크립트가 DOM을 수정하면 업데이트가 발생한다. 

![image-20240616180837672](https://raw.githubusercontent.com/oiosu/image_repo/master/img/image-20240616180837672.png)

* DOM이 수정되면 브라우저는 Critical Rendering Path 의 전체 단계를 다시 진행한다. 
* 그래서 렌더 트리를 다시 생성하고 레이아웃을 잡고 다시 페인팅을 진행한다.
* 주의할점 
  * Critical Rendering Path의 전체 과정들 중에 3단계에 해당하는 레이아웃과 4단계에 해당하는 페인팅은 꽤 오래 걸리는 과정이다.
  * 그렇기 때문에 DOM이 수정되어서 레이아웃을 진행되는 것을 **Reflow** 라고 하고 비슷한 이유로 페이팅과정이 다시 진행되는 것을 **Repaint** 라고 불린다.

##### 😡 Super Bad Practice

* 3000번 DOM 수정, 성능 측정 결과 : 4,500ms

```html
<script>
    function onClick() {
        const $ul = document.getElementById("ul");
        for(let i = 0; i < 3000; i++) {
            $ul.innerHTML += `<li>${i}</li>`;
        }
    }
</script>
<body>
    <button onClick="onClick()">
        리스트 추가하기
    </button>
    <ul id="ul">
    </ul>
</body>
```

* DOM은 딱 한번만 수정함, 성능 측정 결과 : 250ms (약 22배 개선 됨)

        const $ul = document.getElementById("ul");

> 반복문 내부에서 innerHTML을 바로 수정하는 것이 아닌 앞서 선언한 list라는 변수에 li 태그를 3000개를 추가하고 있다.  

> 그래서 반복문 내부에서는 DOM 수정을 발생시키지 않게 된다. 



* 동시에 발생하는 다양한 업데이트들이 있을때  업데이트들이 한번 다 DOM을 수정시키도록 만드는 것이 아니라 어딘가의 변수라든지 등 장소에 업데이트들을 다  모아두었다가 한 번만 DOM을 숮어할 수 있도록 각별히 신경써줘야 한다. 
*  React는 이 과정을 자동으로 해준다. (Feat. Virtual DOM)
  * 동시에 발생한 업데이트들을 모아서 DOM 수정 횟수를 최소화 하는 이 작업을 리액트에서는 신경쓰지 않아도 자동으로 처리가 가능하다. 



#### 🤔 Virtual DOM

* DOM을 자바스크립트 객체로 흉내낸 것으로 일종의 복제판 이라고 생각하면 된다. 
* React는 업데이트가 발생하면 실제 DOM을 수정하기 전에 이 가상의 복제판 DOM에 먼저 반영해본다. 
  * 연습 스윙 같은 느낌이라고 생각하면 된다.
